# 기술 조사 → 자산화 전체 파이프라인 오케스트레이터

이 스킬은 **얇은 래퍼**다. 각 단계의 실제 로직은 이미 존재하는 전문 스킬이 갖고 있고, 이 스킬은 그것들을 올바른 순서로 호출하고, 단계 사이에 끊어야 할 지점(사람 확인)을 지키고, 한 곳에만 존재하는 새 단계(원문단계 팩트체크)를 끼워 넣는 역할만 한다. **개별 스킬의 규칙을 이 파일에 복붙하지 않는다** — 규칙이 바뀌면 해당 스킬 파일만 고치면 전체 파이프라인에 자동 반영되게 하기 위함이다.

파이프라인 전체가 다루는 대상은 하나의 vault(`raw/`, `Cards/`, `Blog-drafts/`, `Scratch/`, `Templates/` 5개 폴더 체제)이며, 그 vault의 `CLAUDE.md`가 최종 규칙이다. 각 하위 스킬을 호출할 때 vault 경로를 알고 있으면 인자로 넘긴다.

## 체크포인트 정책 (전 단계 공통)

이 오케스트레이터는 **기계적으로 판단 가능한 것은 자동 처리하고, 사람의 판단이 필요한 지점에서는 반드시 멈춘다.** 아래 CP1~CP6가 그 지점이다. 체크포인트를 스킵하거나 "일단 진행하고 나중에 물어보자"로 미루지 않는다 — 승인 전에 다음 단계로 넘어가지 않는다.

| # | 위치 | 멈추는 이유 |
|---|---|---|
| CP1 | 원문단계 팩트체크 후 | "불일치"·"미확인" 항목을 어떻게 할지(제외/재검색/근거약함 표시 유지)는 판단이 필요함 |
| CP2 | 카드화 완료 후 | 여러 카드 중 어떤 걸 블로그로 승격할지는 사람 몫 (tech-research-card 자체 체크포인트) |
| CP3 | 블로그 승격 후 | 실측치 공백·이미지 슬롯처럼 사람이 채워야 하는 지점이 있으면, 채우기 전에 팩트체크로 넘어갈지 확인 |
| CP4 | 블로그 팩트체크 후 | "불일치"·"미확인" 항목의 수정/삭제/재검색 여부 (tech-wiki-factcheck 자체 체크포인트) |
| CP5 | 휴머나이즈 후 | 등급 B 이하면 heavy 재실행 여부 안내 (humanize-korean 자체 체크포인트) |
| CP6 | vault 구조 감사 중 | 최상위 문서/폴더 위반 삭제, 번호코드 리네임, 애매한 깨진 링크 수정은 승인 필요 (tech-wiki-audit 자체 체크포인트) |

## Phase 0: 입력 확인

사용자가 붙여넣은 대화, 또는 "지난 OO 조사 대화"처럼 과거 대화를 가리키는 참조를 확인한다. vault 경로를 모르면 먼저 확인한다. 이미 raw 파일이 있는 상태에서 이 파이프라인을 호출했다면(예: "이 raw 파일로 나머지 파이프라인 돌려줘") Phase 1을 스킵하고 Phase 2부터 시작한다.

## Phase 1: 원문 저장 (위임 — 0단계만)

`Skill(tech-research-card)`을 호출한다. 단, 인자에 다음을 명시한다:

> "이번엔 0단계(원문 저장 + 태깅)까지만 실행하고 멈춰줘. 1단계(깊이 게이트)·2단계(카드 생성)는 진행하지 마. 저장된 raw 파일의 전체 경로만 알려줘."

tech-research-card는 그 자리에서 로드되는 지침이므로(별도 서브에이전트가 아님) 이 지시를 그대로 따르면 0단계만 실행하고 멈춘다. 결과로 `raw/[제목].md` 경로를 확보한다.

## Phase 2: 원문단계 팩트체크 (신규 로직 — 위임 대상 없음)

이 파이프라인에서 유일하게 새로 작성하는 단계다. 목적: raw에 달린 `[검색확인: URL]`/`[AI진술-미검증]` 태그가 붙은 주장들을 실제로 재검증해서, 근거가 부실한 내용이 카드로 넘어가기 전에 걸러낸다. `tech-wiki-factcheck`와 검증 방법론(개별 검색, 확인됨/불일치/미확인 3분류, 벤치마크 존재·수치 일치·귀속 정확성 3축 확인)은 동일하되, 대상이 Blog-drafts가 아니라 방금 저장한 raw 파일이라는 점만 다르다.

1. raw 파일을 읽고, 태그가 붙은 구체적 주장(수치·벤치마크명·통계) 전부를 목록으로 뽑는다. `[실측]` 태그는 사용자 직접 측정이므로 검증 대상이 아니다.
2. 각 주장을 **개별적으로** 웹 검색해서 확인됨/불일치/미확인으로 분류한다(방법론은 tech-wiki-factcheck의 3번·4번 항목과 동일 — 벤치마크/논문 실재 여부, 수치 정확한 일치, 귀속의 정확성 세 가지를 따로 확인한다. 귀속 오류 — 비슷한 다른 연구 결과가 잘못 붙는 것 — 가 제일 놓치기 쉬우니 특히 주의).
3. **raw에 이미 적힌 텍스트는 절대 수정하지 않는다** (vault 기본 원칙). 검증 결과는 raw 파일 맨 끝에 `## 팩트체크 결과` 섹션을 **추가**해서 표로 남긴다: `| 주장 | 분류 | 근거/문제 |`. 이건 최초 저장의 연장이므로(아직 파이프라인 진행 중) append이지 "이미 저장된 raw를 나중에 고치는" 것이 아니다 — 이 파이프라인을 통해 이번에 처음 저장하는 raw이므로 허용된다. 이미 예전에 저장되어 완결된 raw 파일을 이 단계에서 다시 열어 고치지는 않는다.
4. **CP1**: "불일치"·"미확인" 항목이 있으면 사용자에게 보여주고 확인한다 — 카드화에서 제외할지, 재검색해볼지, 근거 약하다는 표시를 달고 그대로 둘지. 전부 "확인됨"이거나 사용자가 이미 결론을 준 경우(예: "제한적확인, 확인된 사실로 카드화해줘"처럼 미리 방침을 정해준 경우)만 확인 없이 다음 단계로 진행한다.

## Phase 3: 카드화 (위임 — 1~2단계)

`Skill(tech-research-card)`을 다시 호출한다. 인자에 다음을 명시한다:

> "raw 파일은 이미 `raw/[제목].md`에 저장되어 있고 팩트체크 결과 섹션도 append돼 있어. 0단계는 재실행하지 말고 1단계(깊이 게이트)부터 시작해. 카드화할 때 raw의 '팩트체크 결과' 섹션에서 **불일치·미확인으로 분류된 항목은 카드에 포함하지 말 것** — 확인됨·제한적확인 항목만 사용하고, 카드 신뢰도는 그중 가장 약한 등급을 기준으로 보수적으로 잡아줘."

완료 후 tech-research-card 자체의 완료 체크포인트(**CP2**: 어떤 카드를 블로그로 승격할지)를 그대로 따른다.

## Phase 4: 블로그 승격 (위임)

CP2에서 사용자가 승격 대상을 정하면, `Skill(tech-research-card-blog)`를 카드 경로(들)와 함께 호출한다. 카드가 여러 개면 하나로 묶어서 승격할지 각각 별도 글로 승격할지도 이 시점에 확인한다(이미 CP2에서 다뤄지지 않았다면).

완료 후 **CP3**: tech-research-card-blog가 보고하는 "사람이 채워야 하는 지점"(실측치 공백, 이미지 슬롯, 필명귀속 문구)이 있으면, 그걸 먼저 채울지 아니면 채우지 않은 채로 팩트체크·휴머나이즈를 먼저 진행할지 사용자에게 확인한다. 실측치 공백이 팩트체크 대상 수치와 겹치면 먼저 채우는 쪽을 권장한다.

## Phase 5: 블로그 팩트체크 (위임)

`Skill(tech-wiki-factcheck)`를 해당 `Blog-drafts/[제목].md` 경로와 함께 호출한다. **CP4**(불일치·미확인 항목 조치)는 tech-wiki-factcheck 자체 체크포인트를 그대로 따른다. 완료되면 그 스킬이 frontmatter `status`를 `팩트체크 완료`로 갱신하고 `log.md`에 기록하는 것까지 맡긴다.

## Phase 6: 휴머나이즈 (위임)

`Skill(humanize-korean:humanize-korean)`을 같은 블로그 초안 경로와 함께 호출한다.

**환경 주의**: 이 스킬은 정량 채점(`prepare_monolith_input.py`)과 결정적 게이트(`verify_gates.py`)에 Python을 요구한다. 실행 전에 `python3 --version`으로 확인한다. Python이 없으면(Windows에서 App Execution Alias만 있고 실제 인터프리터가 없는 경우가 흔함) route_hint 없이 규칙상 standard 경로로 간주하고, 진단(`humanize-diagnostician`) → 겨냥 윤문(`humanize-monolith`) 2콜을 수동으로 순서대로 호출한다. 이 경우 결정적 게이트가 없으므로 **윤문 결과를 원문과 직접 대조해서 검토** — 특히 의미가 깨지거나 문법이 어색해진 문장(관용구 일부 탈락 등)이 있는지 사람이 봐야 놓치는 부분을 잡는다. 발견되면 그 자리에서 최소 수정 후 반영한다.

완료 후 **CP5**: 등급 B 이하면 heavy(`--strict`) 재실행을 안내하고 사용자 판단을 구한다. A/B 등급 이상이고 사람 검토로도 문제가 없으면 status를 `윤문 완료`로 갱신.

## Phase 7: vault 구조 감사 (위임)

`Skill(tech-wiki-audit)`를 호출한다. **CP6**(A/B/D/F 항목의 삭제·리네임·수정 승인)는 그 스킬 자체 체크포인트를 그대로 따른다.

## Phase 8: 최종 보고

파이프라인 전체를 한 화면에 요약해서 보여준다:
- 생성/수정된 파일 목록 (raw 1개, 카드 N개, 블로그 초안 1개 이상)
- 각 단계의 최종 상태 (팩트체크 완료 여부, 윤문 등급, vault 감사 결과)
- CP1~CP6에서 사용자가 내린 결정 요약
- 아직 열려 있는 후속 질문(카드의 "다시 물어볼 질문" 필드에 쌓인 것들)

## 흔한 실수 — 반드시 피할 것

- **Phase를 건너뛰거나 순서를 바꾸지 않는다.** 특히 Phase 2(원문단계 팩트체크)를 생략하고 바로 카드화로 가면, 이 오케스트레이터를 만든 이유 자체가 없어진다.
- **하위 스킬의 로직을 이 파일에 베껴 쓰지 않는다.** 하위 스킬이 업데이트되면 이 오케스트레이터는 그대로 최신 로직을 상속해야 한다 — 안 그러면 두 곳이 어긋난다.
- **체크포인트를 자동 승인하지 않는다.** "불일치 항목 3개 있는데 그냥 다 빼고 진행할게요" 식으로 사용자 결정을 대신 내리지 않는다. 특히 vault 파일 삭제·리네임(CP6)은 되돌리기 번거로우니 반드시 승인 후 실행.
- **raw 파일을 두 번 저장하지 않는다.** Phase 1에서 이미 저장했으므로 Phase 3에서 tech-research-card를 다시 호출할 때 0단계를 재실행하지 말라고 명시적으로 지시해야 한다.
