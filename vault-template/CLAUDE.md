# 기술 조사 위키 작업 규칙

**Vault 경로**: `<이 vault의 절대 경로로 바꿀 것>`
- 스킬 및 도구들은 이 경로를 기준으로 작업합니다.
- `raw/`, `Cards/`, `Blog-drafts/` 등 모든 폴더는 이 경로 하위에 있습니다.

이 vault는 기술 조사·학습 대화를 개인 자산 카드로 정리하고, 필요하면 블로그로 승격하는 용도다.

## 구조 제약 (반드시 지킬 것 — 문서 증식 방지)

- 이 vault의 최상위 문서는 `CLAUDE.md`, `index.md`, `log.md` **세 개뿐이다.**
- `WORKFLOW.md`, `_lineage.md`, 폴더별 `README.md` 같은 새 안내/설명 문서를 **만들지 않는다.**
  - 규칙이 바뀌면 → 이 파일(`CLAUDE.md`)을 고친다.
  - 안내가 필요하면 → `index.md`만 고친다.
  - 처리 이력은 → `log.md`에 한 줄만 추가한다.
- 폴더는 `raw/`, `Scratch/`, `Cards/`, `Blog-drafts/`, `Templates/` 다섯 개뿐이다. 날짜·프로젝트별 하위 폴더를 새로 만들지 않는다 — 모든 파일은 해당 폴더에 평평하게(flat) 쌓는다. 검색과 연결은 옵시디언 링크·백링크·그래프뷰가 담당한다.
  - **예외: `Scratch/`만 글 단위 하위 폴더를 둔다** (`Scratch/<짧은영문슬러그>/`). 팩트체크·휴머나이즈 중간산출물·이미지 원본(`images/`)을 글 하나에 한 폴더로 모은다. Scratch는 git에서 제외된 임시 작업 공간이라 그래프·이력에 남지 않는데, 평평하게 쌓으면 글 여러 개의 중간산출물이 섞여 어느 파일이 어느 글 것인지 헷갈린다. 슬러그는 경로 사고를 피하려고 ASCII로 쓴다.
- 파일명은 **내용을 설명하는 제목 그대로** 쓴다 (`001_toolkit.md` 같은 번호 코드 금지). 번호 코드는 그래프뷰에서 무의미한 라벨이 되고, 별도 사전(README)이 있어야 뭔지 알 수 있게 만들어서 문서를 증식시킨다.

## 링크 배치 규칙 (반드시 지킬 것 — 깨진 링크 방지)

- **위키링크(`[[...]]`)는 frontmatter(YAML)에 절대 넣지 않는다. 본문에만 쓴다.**
  - 이유: YAML은 `[`로 시작하는 값을 리스트(배열)로 파싱한다. `source: [[제목]]`처럼 따옴표 없이 쓰면 위키링크가 아니라 중첩 리스트로 잘못 해석되어, 옵시디언이 백링크·그래프뷰에서 인식하지 못한다.
  - frontmatter에는 날짜·상태·태그 같은 순수 메타데이터만 넣는다 (`stage`, `created_date`, `skill`, `tags` 등).
  - 원문·관련 카드·다음 단계 참조는 전부 본문에 `- 원문: [[제목]]`, `- 관련 문서: [[제목]]` 형식의 텍스트 줄로 쓴다. 카드 템플릿(아래)의 필드가 이미 이 형식이므로 그대로 따르면 된다.
- 파일 경로가 아니라 **파일명만** 링크에 쓴다 (`[[raw/제목]]`이 아니라 `[[제목]]`). 옵시디언은 vault 전체에서 유일한 파일명으로 링크를 해석하므로 폴더 경로가 없어도 연결된다. 경로를 넣으면 파일을 옮길 때마다 링크가 깨진다.

## 기본 원칙

- `raw/` 안의 원본 대화 텍스트는 임의로 수정하지 않는다.
- 정리된 카드는 `Cards/`에 마크다운으로 작성한다.
- 공개용 초안은 `Blog-drafts/`에 둔다.
- 새 카드/초안을 만들면 `index.md`의 목록과 `log.md`에 한 줄 기록을 추가한다. `log.md`는 `| 날짜 | 작업 | 환경 | 근거/결과 | 확인 필요 |` 형식이며, **환경** 칸에 이 작업이 어디서 실행됐는지(`Claude Code` / `Cowork` / `claude.ai`)를 반드시 적는다 — 여러 환경에서 같은 vault를 건드리면 나중에 "이거 어디서 한 거였지"를 추적할 유일한 단서가 이 칸이다.

## 0단계: 원문 저장 (근거 오염 방지 — 태깅 필수)

카드를 만들기 전에, 확보한 대화 원문을 가공 없이 그대로 `raw/[제목].md`로 먼저 저장한다. 제목은 조사 주제를 짧게 요약한 것.

**저장하면서 구체적 주장(수치·벤치마크명·통계)마다 그 자리에 태그를 단다:**

- `[실측]` — 사용자가 직접 측정·실행한 결과
- `[검색확인: URL]` — 그 대화 안에서 실제로 웹검색·문서 조회를 해서 확인한 내용
- `[AI진술-미검증]` — AI가 검색 없이 자기 지식만으로 말한 내용

**이게 왜 중요하냐면**: "raw에 적혀있다"는 게 근거로 취급되기 쉬운데, 그 대화에서 AI가 검색 없이 진술한 내용이 섞여 있으면 raw 자체가 오염된 근거가 된다. `raw/`는 "수정하지 않는다"는 원칙 때문에 이 오류가 그대로 보존되므로, 저장 시점에 태깅하는 것만이 나중에 이걸 구분할 유일한 방법이다. 태깅은 판단이 아니라 사실 확인이다 — 그 대화에서 검색 도구를 실제로 호출했는지는 명확히 알 수 있으므로 정직하게 표시한다.

**2단계로 넘어갈 때**: raw에서 `[AI진술-미검증]` 태그가 붙은 내용을 카드에 옮기면, 그 카드의 신뢰도는 절대 "확인됨"이나 "제한적확인"으로 시작할 수 없다 — "확인필요"로 두고, 4단계 팩트체크에서 실제로 외부 검증된 뒤에만 신뢰도를 올린다.

## 1단계: 깊이 게이트 분류

대화에 등장하는 개념을 4가지로 분류한다.

- **핵심개념**: 원래 조사 대상 그 자체 → 별도 카드
- **핵심전제**: 핵심개념 설명에 필요한 일반 개념 → 카드 본문에 1~2문장 인라인 정의만
- **비교 필수 대상**: 카드의 비교표를 채우기 위해 필요한 대상 → 표 한 줄 분량만 파악
- **인접배경**: 필수는 아님 → `#추후조사` 태그만 달고 스킵

흔한 실수: 핵심개념의 고유 메커니즘을 핵심전제로 잘못 분류하지 말 것(그건 본문 그 자체). 비교 대상을 인접배경으로 스킵하지 말 것(표가 필수 요구).

## 2단계: 카드 템플릿

`Templates/card-template.md`를 따른다.

**신뢰도 4단계 기준**
- 확인됨: 직접 실측했거나 원문헌에 명시적으로 적혀 있음
- 제한적확인: 근거는 있으나 범위가 좁음 (단일 소스, 소규모 테스트)
- 추정: 가능성을 말하는 해석, 직접 근거 없음
- 확인필요: 근거 없이 단정하면 위험한 내용

**출처유형 규칙**: 실측 아닌 수치를 사용자 결과처럼 쓰지 않는다. 문헌조사면 "○○ 문서에서는 A라고 보고했다"처럼 귀속해서 서술한다.

**다시 물어볼 질문**: 모든 카드는 이 섹션을 채운다. 카드를 닫힌 결과물이 아니라 다음 질문의 출발점으로 남기기 위함이다.

## 새 카드를 만들 때 (연결 자동화)

새 카드를 만들기 전에 `Cards/` 폴더의 기존 파일 제목을 먼저 확인한다. 관련 있는 기존 카드가 있으면 "관련 문서" 필드에 `[[제목]]` 형식으로 자동으로 링크한다.

## 3단계: 블로그 승격 (요청 시에만)

- **경로**: `Cards/`의 카드들을 묶어 `Blog-drafts/[제목].md`에 평평하게 저장한다 (1·2단계와 동일한 flat 규칙).
- 카드의 질문형 제목을 그대로 섹션 제목으로 승격한다.
- "신뢰도: 확인필요/추정"인 내용은 블로그에 단정문으로 옮기지 않는다.
- 이미지는 `{이미지: 유형 | 설명 | 용도}` 슬롯으로 표시 (유형: 다이어그램/실측 스크린샷/일러스트).
- 본문에 필명귀속 문구를 넣는다.
- AI스러운 문체(공허한 전환구, 3항 나열, 과장된 강조어)를 피한다.
- frontmatter에는 `stage`, `created_date`, `status`(예: `초안`)만 넣는다. 원문·참고 카드 링크는 본문에 `- 원문: [[제목]]`, `- 참고 카드: [[제목]]`로 쓴다 (링크 배치 규칙 참고).

## 4단계: 팩트체크 (문헌조사 기반 초안은 필수)

"출처유형: 문헌조사"가 하나라도 있는 블로그 초안은 게시 전에 반드시 이 단계를 거친다. 실측 기반만 있는 초안은 생략 가능.

- **경로**: 검색 과정·발견 사항은 `Scratch/<슬러그>/[제목]-factcheck.md`에 임시로 남긴다 (git 추적 제외, 영구 보관 안 함).
- 초안에 등장하는 구체적 수치·벤치마크명·통계는 각각 웹 검색으로 원 출처를 재확인한다.
- 확인 결과를 3가지로 분류한다: **확인됨**(원 출처와 정확히 일치) / **불일치**(출처는 실재하나 수치·맥락이 다름) / **미확인**(원 출처를 못 찾음).
- "불일치"·"미확인" 항목은 게시 전에 수정하거나 삭제해야 한다 — 그냥 넘기지 않는다.
- 완료되면 `Blog-drafts/[제목].md`의 `status`를 `팩트체크 완료`로 갱신한다.

## 5단계: 휴머나이즈 (선택, 문체 진단·윤문)

블로그 초안의 AI 티를 진단하고 자연스럽게 다듬는 단계. **진단 과정의 중간 산출물(문제 패턴 목록, 변경률 등)은 `Scratch/`에 임시로 두고, vault에 영구 보관하지 않는다** — 이건 감사 대상 지식 자산이 아니라 작업 중 메모다. 최종 결과만 `Blog-drafts/`의 해당 파일을 직접 덮어써서 반영한다. 별도 폴더(`Humanize/` 등)를 새로 만들지 않는다. 완료되면 `status`를 `윤문 완료`로 갱신한다.
