# 3단계: 블로그 승격 (참고)

자산화 카드를 공개 블로그 글로 승격할 때 참고한다. 이 단계는 기본 실행 범위가 아니며, 사용자가 명시적으로 요청할 때만 진행한다.

## 승격 원칙

- 카드의 **질문형 제목**을 그대로 블로그 섹션(H2/H3) 제목으로 쓴다 — 재작성하지 말고 승격만 한다.
- 카드의 **비교표·수치**는 구조 그대로 유지한다. 이런 구조화(정의/비교표/수치)가 검색·AI답변 노출에도 유리하다.
- **출처유형이 "문헌조사"인 카드**는 GEO(생성엔진최적화) 관점에서 우선순위를 낮게 잡는다 — 이미 원문헌·공식문서가 그 자리를 차지하고 있어서, 경쟁 소스 없는 실측 콘텐츠보다 노출 우위가 없다. 그래도 개인 자산화 목적으로는 여전히 유효하니, 게시 여부는 사용자 판단에 맡긴다.
- 범용 개념 설명(이미 답이 넘치는 주제)보다, 사용자의 실측 경험·특이 사례처럼 경쟁 소스가 없는 콘텐츠를 승격 우선순위로 둔다.

## 사람이 반드시 채워야 하는 지점 (자동 완성하지 말 것)

1. **실측치**: "출처유형: 실측" 카드의 예시 섹션에 실제 수치가 비어 있다면, 반드시 사용자에게 요청한다. 임의로 수치를 만들어 넣지 않는다.
2. **이미지 슬롯**: 아래 "이미지 슬롯 설계" 규칙에 따라 처리한다. 유형에 따라 자동 생성/사용자 확인이 나뉜다.
3. **필명귀속 문구**: 본문 안에 "이 글은 필자가 직접 측정한 결과를 포함한다" 류의 귀속 문구를 넣는다. AI가 답변을 요약할 때 링크만 인용하고 이름은 빠지는 "고스트 인용"을 줄이기 위함이다.

## 이미지 슬롯 설계

블로그 초안에 이미지가 필요한 자리는 바로 파일을 찾지 말고, 아래 문법으로 슬롯을 먼저 박아둔다:

```
{이미지: 유형 | 설명 | 용도}
```

유형은 세 가지뿐이고, 유형마다 처리 방식이 다르다. 유형 판단을 잘못하면 안 되므로 아래 표를 정확히 따를 것.

| 유형 | 언제 쓰나 | 처리 방식 |
|---|---|---|
| **다이어그램** | 개념·구조·흐름을 설명하는 이미지 (아키텍처, 프로세스, 비교 구조 등) | **직접 제작.** "설명" 필드를 그대로 diagram 스킬(mermaid 또는 matplotlib)에 넘겨서 그린다. 검색하지 않는다. |
| **실측 스크린샷** | 본인이 직접 돌린 결과의 캡처 (벤치마크, 대시보드, 터미널 출력 등) | **사용자에게 요청.** "이 자리에 [설명]에 해당하는 본인 실측 캡처를 붙여줘"라고 명시적으로 요청한다. 대신 만들거나 남의 캡처를 대체하지 않는다. |
| **일러스트** | 개념적으로 대체 가능한 도입부·분위기용 이미지 (특정 데이터를 담지 않는 것) | **비전 모델 프롬프트 후보 제시.** 아래 "일러스트 프롬프트 생성 규칙"에 따라 프롬프트 문자열을 만들어 사용자에게 제시하고, 실제 생성/선택은 사용자가 확정한다. |

예시:
```
{이미지: 다이어그램 | vLLM PagedAttention의 KV캐시 블록 매핑 구조, OS 페이징과 비교 | 메커니즘 설명}
{이미지: 실측 스크린샷 | 본인 서빙 환경에서 측정한 처리량 그래프 | 성능 비교 근거}
{이미지: 일러스트 | 서버랙과 GPU를 형상화한 추상적 이미지, 다크블루 톤 | 글 도입부 후킹}
```

### 다이어그램 슬롯 처리

`{이미지: 다이어그램 | ...}` 슬롯을 만나면, 그 자리에서 바로 diagram 스킬을 불러 "설명" 필드 내용으로 그린다. 카드의 "인접 개념과의 차이" 표가 이미 있다면 그 표 내용을 다이어그램의 재료로 재사용한다 — 새로 조사하지 않는다.

### 일러스트 프롬프트 생성 규칙

"설명" 필드를 아래 구조의 프롬프트 문자열로 변환해서 사용자에게 제시한다:

```
[스타일: 예. 플랫 일러스트/미니멀 라인아트/사진풍] +
[핵심 요소: 설명 필드의 대상] +
[색감/톤: 설명 필드에 있으면 반영, 없으면 사용자에게 확인] +
[구성: 여백·비율 등 블로그 히어로 이미지에 맞는 구도]
```

제약 (반드시 지킬 것):
- 실존 인물, 특정 회사 로고·제품 디자인, 저작권 있는 캐릭터를 프롬프트에 넣지 않는다 — 전부 형상화된 추상 표현으로 대체한다 (예: "NVIDIA GPU" → "GPU 칩을 형상화한 추상 아이콘").
- 프롬프트만 제시하고, 실제 이미지 생성/검색 실행은 사용자가 "이 프롬프트로 만들어줘"라고 확정한 뒤에 진행한다.

## 저작권 주의

원문헌·공식문서를 인용할 때는 15단어 미만의 짧은 인용만 쓰고, 문장은 직접 서술로 재구성한다. 수치나 사실은 재인용해도 되지만 문장 구조를 그대로 베끼지 않는다.

## AI스러운 문체 피하기

GEO 관점에서는 구조화(정의·비교표·수치)가 유리하지만, 그것과 별개로 **문장 자체가 AI 생성물처럼 읽히면 독자가 불편함을 느낀다.** 이건 노출과는 다른 차원의 문제이므로 구조화 원칙과 별도로 지킨다.

승격된 초안에서 아래 패턴이 보이면 사람이 쓴 것처럼 다듬는다:

- **공허한 도입/전환 문구 제거**: "흥미롭게도", "주목할 점은", "결론적으로", "이는 ~를 시사한다" 같은, 내용 없이 문장을 이어붙이기만 하는 표현을 없앤다. 바로 내용으로 들어간다.
- **과도한 3항 나열 피하기**: "빠르고, 안전하고, 확장 가능한" 식으로 형용사 세 개를 습관적으로 붙이지 않는다. 실제로 세 개가 다 필요한지 확인하고, 보통 하나면 충분하다.
- **문장 길이에 리듬 주기**: 모든 문장이 비슷한 길이·구조로 이어지면 기계적으로 읽힌다. 짧은 문장과 긴 문장을 섞는다.
- **불필요한 헤징 줄이기**: "~일 수도 있다", "~라고 볼 수 있다"를 남발하지 않는다. 카드에 이미 확인된 사실(실측/문헌조사로 출처가 명확한 것)은 단정적으로 쓴다. 헤징은 진짜 불확실한 부분에만 남긴다.
- **과장된 강조 어휘 자제**: "혁신적인", "게임체인저", "완전히 바뀐다" 같은 표현은 실측 기반 기술 글에 안 맞는다. 구체적 수치·비교로 대체한다.
- **일반화된 요약 문단 지양**: 글 끝에 앞 내용을 다시 요약하는 문단을 습관적으로 붙이지 않는다. 새로 덧붙일 내용이 없으면 그냥 끝낸다.

이 점검은 카드를 블로그로 승격하는 마지막 단계에서 한 번 훑는 정도로 충분하며, 모든 문장을 기계적으로 다 고치려 하지 않는다 — 자연스럽게 읽히는지가 기준이다.

### 어미 예시 (구어체로 쓸 때, 추상적 지시만으로는 안 지켜짐)

"구어체로 써라"는 지시만으로는 모델이 규칙을 기계적으로만 적용해서 어미가 흔들린다. 아래처럼 Incorrect/Correct 짝으로 실제 어미를 명시한다.

```
Incorrect: ~하였습니다 / ~함 / ~이다
Correct: ~했어요 / ~하는 거예요 / ~예요

Incorrect: ~할 수 있습니다 / ~됩니다
Correct: ~할 수 있어요 / ~돼요

Incorrect: ~하는 반면 / 그러나
Correct: ~하는데 / 근데
```

### 문장 끝 통일성 자체 점검 (마지막 패스)

초안을 다 쓴 뒤, 별도 패스로 아래만 다시 훑는다. 내용을 새로 쓰지 않고 어미만 확인한다.

1. 모든 문장이 "-요"체로 끝나는지 확인한다. "-다"체("~이다", "~한다")가 섞여 있으면 "-요"체로 통일한다.
2. 같은 문단 안에서 종결형이 갑자기 격식체("-습니다")로 바뀌는 지점이 없는지 확인한다.
3. 이 패스에서 발견한 것만 고치고, 문장 구조나 내용은 건드리지 않는다.

## 서술모드 (실측+시행착오 경험이 있는 카드에만)

기본 승격(위 원칙)은 정의·비교 중심 카드에 맞는 **구조모드**다. 카드에 "시도 → 실패 → 원인 진단 → 재설계"의 실제 경험이 있으면(예: 성능 측정 리트랙션, 파이프라인 재설계 경험), 아래 **서술모드**를 대신 쓸 수 있다. 문헌조사 카드나 정의/비교 카드에는 서술모드를 쓰지 않는다 — 실제 시행착오 서사가 없으면 억지로 이야기를 만들게 된다.

**서술모드 구조:**
1. **사건형 제목**: 질문형이 아니라 "무슨 일이 있었는지"를 제목에 쓴다. (예: "리랭커 성능, 발표 후 제가 직접 취소했습니다")
2. **화자 명시로 시작**: 첫 문단에 필명귀속을 배치한다.
3. **숫자로 문제 제시**: 실측치(카드의 "예시" 필드)로 문제 상황을 구체화한다. 지어내지 않는다.
4. **사건형 소제목**: "그래서 발표를 취소했어요" 처럼 명사형이 아니라 사건 중심으로 소제목을 단다.
5. **실패 원인을 숨기지 않고 진단**: 카드의 신뢰도가 "확인됨"인 원인만 단정적으로 쓰고, "추정"인 부분은 표시한다.
6. **즉시 실물 제시**: 원칙을 설명하는 대신 실제로 쓴 문서/코드 구조를 그대로 보여준다.
7. **미완결로 마무리**: 완벽한 결론 대신 "아직 진행 중"인 다음 행동을 예고한다.

**트레이드오프 — 사용자에게 반드시 알릴 것**: 서술모드는 사건형 제목을 쓰기 때문에 구조모드보다 GEO(질문형 제목 기반 인용 노출)에 불리하다. 이 트레이드오프를 승격 전에 사용자에게 한 줄로 알리고, 필요하면 메타디스크립션에 질문형 문장을 별도로 넣는 절충안을 제안한다.
