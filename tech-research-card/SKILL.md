# 기술 조사 → 자산화 카드 변환

기술 조사·학습 대화(Claude/GPT와 나눈 원문)를 개인 자산화용 카드로 압축하는 스킬. 목적은 "새 용어를 만날 때마다 끝없이 깊게 파고들어 정리를 포기하게 되는" 병목을 끊는 것이다. 핵심 메커니즘은 용어 단위의 "깊이 게이트"로, 무엇을 깊게 다룰지와 무엇을 스킵할지를 그 자리에서 즉시 결정한다.

이 스킬은 파이프라인의 1~2단계(깊이 게이트 분류 → 카드 생성)를 담당한다. 처음엔 분류·템플릿 채우기가 기계적이라 보고 `model: haiku`로 지정했었는데, 실제 사용해보니 "핵심전제 vs 비교필수" 같은 경계 판단이 미묘해서 정확도가 떨어졌다 — `sonnet`으로 상향. 3단계(블로그 승격)는 별도 스킬 `tech-research-card-blog`가 담당한다.

## 실행 순서

### 0. 입력 확보 및 원문 저장

- 사용자가 대화를 붙여넣었다면 그것을 그대로 입력으로 쓴다.
- 사용자가 "지난 vLLM 조사 대화" 처럼 특정 과거 대화를 가리키면, `conversation_search`나 `recent_chats`로 해당 대화를 찾아 원문을 가져온다.
- 대화 하나에 여러 주제가 뒤섞여 있어도 별도 전처리(주제 분리)는 하지 않는다 — 아래 1단계 게이트가 관련 없는 내용을 자연스럽게 걸러낸다. 이건 의도된 설계이므로 주제 분리 로직을 추가하지 말 것.
- **vault에 파일을 쓸 수 있는 환경(Claude Code 등)에서는, 분류를 시작하기 전에 확보한 원문을 가공 없이 그대로 `raw/[제목].md`에 저장한다.** 제목은 조사 주제를 짧게 요약한 것으로 정한다(예: "vLLM 서빙 아키텍처 조사"). 이미 같은 제목의 raw 파일이 있으면 사용자에게 덮어쓸지 새 제목으로 할지 확인한다. 이 저장을 빠뜨리면 카드의 "원문:" 링크가 걸 대상이 없어진다.
- **저장하면서 구체적 주장(수치·벤치마크명·통계)마다 태그를 단다: `[실측]` / `[검색확인: URL]` / `[AI진술-미검증]`.** "raw에 적혀있다"는 게 근거로 취급되곤 하는데, 그 대화에서 AI가 검색 없이 진술한 내용이 섞여 있으면 raw 자체가 오염된 근거가 된다. 태깅은 판단이 아니라 그 대화에서 검색 도구를 실제로 호출했는지에 대한 사실 확인이므로 정직하게 표시한다.

### 1단계: 깊이 게이트 분류

대화에 등장하는 개념·용어를 하나씩 아래 4가지로 분류한다. 분류만 하고 넘어가며, 이 단계에서 카드를 완성하지 않는다.

| 분류 | 판단 기준 | 처리 |
|---|---|---|
| **핵심개념** | 사용자가 원래 조사하려던 대상 그 자체 | 2단계에서 별도 카드로 작성 |
| **핵심전제** | 핵심개념을 설명하는 문장이 이것 없이는 성립하지 않는 일반 개념 | 카드 본문에 1~2문장 인라인 정의만 넣고 더 파지 않음 |
| **비교 필수 대상** | 카드 템플릿의 "인접 개념과의 차이" 표를 채우기 위해 필요한 대상(경쟁/유사 기술) | 비교표 한 줄 채울 만큼만 파악, 별도 카드 안 만듦 |
| **인접배경** | 있으면 좋지만 지금 카드 완성에 필수는 아닌 것 | `#추후조사` 태그만 달고 스킵 |

**흔한 실수 — 반드시 피할 것:**
- 핵심개념의 고유 메커니즘(그 기술이 왜 그렇게 동작하는지)을 "핵심전제"로 잘못 분류하지 말 것. 이건 핵심전제가 아니라 핵심개념 카드의 본문 그 자체다. 핵심전제는 그 메커니즘을 설명하는 데 쓰인 *일반* 개념(예: OS 페이징, 양자화)에만 적용한다.
- 비교 대상을 "인접배경"으로 스킵하지 말 것. 카드 템플릿이 비교표를 필수로 요구하므로, 비교 대상은 완전히 미루면 안 되고 표 한 줄 채울 정도로는 파악해야 한다.

출력은 아래처럼 태그가 달린 스크래치 노트 형태로 남긴다:

```
## 탐색 노트: [주제] (YYYY-MM-DD)
- [용어] → 핵심개념 (별도 카드)
- [용어] → 핵심전제: "[1문장 정의]"
- [용어] → 비교 필수 대상: "[한 줄 특징]"
- [용어] → 인접배경 #추후조사
```

### 2단계: 자산화 카드 생성

1단계에서 "핵심개념"으로 분류된 항목마다 아래 고정 템플릿으로 카드를 하나씩 만든다. 섹션마다 분량 캡이 있으니 넘으면 별도 카드로 쪼갤지 사용자에게 확인한다.

```markdown
## [질문형 제목 — 예: "vLLM은 다른 추론 서빙 엔진과 뭐가 다른가?"]

- 정의: (1~2문장. 3문장 넘으면 이미 다른 개념을 설명하는 중이라는 신호 — 분리 검토)
- 왜 중요한가: (1~2문장)
- 인접 개념과의 차이: (표, 비교 대상 1~2개, 1단계의 "비교 필수 대상" 사용)
- 예시: (본인 실측 결과 또는 문헌조사 인용 — 아래 "출처유형" 규칙 참고)
- 신뢰도: [확인됨 / 제한적확인 / 추정 / 확인필요]
- 출처유형: [실측 / 문헌조사]
- 조사일: YYYY-MM-DD
- 관련 문서: [[다른 카드 제목]] (기존 Cards/ 폴더에 관련 카드가 있으면 링크, 없으면 생략)
- 다시 물어볼 질문:
  - (이 카드를 닫힌 결과물이 아니라 다음 질문의 출발점으로 남기기 위해 최소 1개 이상 작성)
```

**신뢰도 4단계 기준:**
- **확인됨**: 직접 실측했거나 원문헌에 명시적으로 적혀 있음
- **제한적확인**: 근거는 있으나 범위가 좁음 (단일 소스, 소규모 테스트)
- **추정**: 가능성을 말하는 해석, 직접 근거 없음
- **확인필요**: 근거 없이 단정하면 위험한 내용

**raw 태그와 신뢰도 연동 (반드시 지킬 것)**: 카드 내용이 raw에서 `[AI진술-미검증]` 태그가 붙은 부분에서 온 것이면, 그 카드의 신뢰도는 "확인됨"이나 "제한적확인"으로 시작할 수 없다 — 무조건 "확인필요"로 시작하고, 4단계 팩트체크(`tech-wiki-factcheck`)에서 외부 검증된 뒤에만 올린다. raw에 근거가 있다는 것과 그 근거가 검증됐다는 것은 다른 문제다.

**출처유형 규칙 (반드시 지킬 것):**
- **실측**: 사용자가 직접 돌려보거나 측정한 결과가 있을 때만. 이 경우 "예시" 섹션에 실제 수치를 넣는다.
- **문헌조사**: 직접 실측 환경이 없을 때. 이 경우 "예시" 섹션에는 수치를 재인용하지 말고, "○○ 논문/공식문서에서는 A가 B라고 보고했다" 식으로 출처를 귀속해서 서술한다. 사용자가 측정하지 않은 걸 사용자의 결과처럼 쓰지 말 것 — 이건 이 스킬의 절대 원칙이다.
- 확실하지 않으면 사용자에게 물어본다: "이 수치, 직접 돌려본 거야 아니면 어디서 본 거야?"

**관련 문서 연결 규칙**: 새 카드를 만들기 전에 기존 카드 목록(vault의 `Cards/` 폴더 또는 사용자가 전달한 목록)을 확인하고, 관련 있는 카드가 있으면 자동으로 `[[제목]]` 링크를 넣는다. 매번 사용자에게 기존 목록을 요청하지 않는다.

카드는 옵시디언/노션에 바로 붙여넣을 수 있는 마크다운으로 출력한다.

## 저장 경로·파일명·링크 규칙 (vault를 직접 다룰 때 반드시 지킬 것)

vault 폴더(`raw/`, `Cards/`, `Blog-drafts/` 등)에 직접 파일을 쓸 수 있는 환경(Claude Code 등)에서는 아래를 지킨다. vault의 `CLAUDE.md`가 있으면 그게 최종 기준이며, 이 규칙과 충돌하면 `CLAUDE.md`를 따른다.

- **경로**: 카드는 `Cards/[제목].md`, 원문은 `raw/[제목].md`에 평평하게(flat) 저장한다. 날짜·프로젝트별 하위 폴더나 번호 코드 파일명(`001_toolkit.md`)을 새로 만들지 않는다.
- **파일명 = 카드/문서 제목 그대로.** 번호 코드를 쓰지 않는다 — 그래프뷰에서 라벨이 무의미해지고, 뭔지 확인하려면 별도 사전 문서가 필요해져서 문서가 계속 늘어나는 원인이 된다.
- **위키링크는 frontmatter에 절대 넣지 않는다.** YAML은 `[`로 시작하는 값을 리스트로 파싱하므로, `source: [[제목]]`처럼 따옴표 없이 쓰면 위키링크가 아니라 깨진 중첩 리스트가 된다. frontmatter에는 `stage`/`created_date`/`skill`/`tags` 같은 순수 메타데이터만 쓰고, 원문·관련 카드 참조는 이 스킬의 템플릿이 이미 정의한 본문 필드(`관련 문서:`, 그리고 원문 참조가 필요하면 `- 원문: [[제목]]`)로만 쓴다.
- **링크에 폴더 경로를 넣지 않는다.** `[[Cards/제목]]`이 아니라 `[[제목]]`만 쓴다 — 옵시디언은 vault 전체에서 고유한 파일명으로 링크를 해석하므로 경로가 없어도 연결되고, 경로를 넣으면 파일 이동 시 링크가 깨진다.
- **새 최상위 안내/설명 문서를 만들지 않는다** (`WORKFLOW.md`, `_lineage.md`, 폴더별 `README.md` 등). vault의 안내판은 `index.md` 하나, 이력은 `log.md` 하나뿐이다. 카드/초안을 새로 만들면 이 두 파일만 갱신한다.

## 링크 검증 (파일 작성 후 매번 필수 — 판단이 아니라 기계적 대조)

카드/원문을 vault에 저장한 뒤, **끝내기 전에 반드시** 아래 검증을 bash로 실행한다. 이건 모델이 "제목을 정확히 기억했는지" 판단에 맡기지 않고, 문자열을 기계적으로 대조해서 깨진 링크를 원천 차단하는 단계다.

```bash
comm -23 \
  <(grep -rho '\[\[[^]]*\]\]' raw Cards Blog-drafts index.md 2>/dev/null | sed 's/\[\[//; s/\]\]//' | sort -u) \
  <(find raw Cards Blog-drafts -name "*.md" | sed 's/.*\///; s/\.md$//' | sort -u)
```

- 출력이 비어있으면 통과.
- 출력에 뭔가 나오면, 그게 실제 파일명과 안 맞는 링크 타겟이다. 방금 만든 파일들의 제목과 비교해서 오타/공백 차이를 찾아 그 자리에서 고친다. 뭐가 맞는지 애매하면 사용자에게 확인하고, 확인 전까지는 그 링크를 `[[ ]]`가 아닌 일반 텍스트로 남긴다.

## 완료 후

카드를 다 만들고 나면, 다음을 수행한다 (파이프라인의 확인 지점):
1. 1단계 분류 중 애매했던 항목이 있었다면 짚어서 사용자 판단을 구한다.
2. 여러 카드가 나왔다면, 이 중 어떤 걸 나중에 블로그로 승격할 후보로 볼지 묻는다 (조합 판단은 사람 몫).
3. `log.md`에 한 줄 기록을 추가한다: `| 날짜 | 작업 | 환경 | 근거/결과 | 확인 필요 |`. **환경** 칸에는 지금 이 스킬이 실행되고 있는 곳(`Claude Code` / `Cowork` / `claude.ai`)을 반드시 적는다 — 여러 환경에서 같은 vault를 건드릴 수 있으므로, 나중에 추적할 유일한 단서다.

블로그 승격은 이 스킬의 범위가 아니다. 승격이 필요하면 `/tech-research-card-blog [카드 경로]`로 별도 스킬을 호출하라고 안내한다.
