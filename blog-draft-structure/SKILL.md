# 블로그 초안 구조 정리

사용자가 **직접 쓴** 블로그 초안에 위계를 부여한다. 글을 대신 써주는 스킬이 아니라, 이미 있는 글의 뼈대만 세워주는 스킬이다.

**기본 입력은 헤딩이 하나도 없는 평문 초안이다.** 사람이 쭉 써 내려간 글이 이 스킬의 정상 케이스이고, 헤딩이 이미 있는 초안이 오히려 예외다. "헤딩이 없어서 분석할 게 없다"는 결론을 내지 않는다 — 헤딩이 없는 상태가 바로 이 스킬이 해결하려는 문제다.

`tech-research-card-blog`와 헷갈리지 말 것 — 그쪽은 카드를 입력으로 받아 초안을 **생성**하고, 이 스킬은 사람이 쓴 초안을 입력으로 받아 구조만 **부여**한다. 초안이 아직 없으면 이 스킬이 아니다.

## 절대 원칙 (다른 모든 지침보다 우선)

- **본문 문장은 어떤 경우에도 수정하지 않는다.** 사용자가 직접 쓴 글이므로 문체·표현·내용·문단 순서를 그대로 유지한다. 매끄럽게 다듬고 싶어지는 지점이 나와도 손대지 않는다. 이 스킬이 파일에 쓰는 것은 **헤딩 줄·리스트 마커·표 마크업·이미지 슬롯**뿐이다.
- **오탈자는 지적만 하고 고치지 않는다.** 보고 항목에 위치와 함께 적어두고, 고치는 건 사용자 몫이다.
- **소제목은 후보를 제안하되 확정하지 않는다.** 문구 후보는 항상 **여러 개를 나란히** 주고, 어느 것을 쓸지는 사용자가 고른다 (4단계). 후보 하나만 던지면 그게 앵커가 되어 사용자의 표현을 밀어낸다.
- **승인 없이 파일을 수정하지 않는다.** 1~7단계는 읽기·제안뿐이고, 쓰기는 9단계에서 승인받은 항목에 한해서만 한다.

## 실행 순서

### 0. 구조 레퍼런스 먼저 읽기

vault에 `Templates/블로그-구조-레퍼런스.md`가 있으면 **초안을 열기 전에 먼저 읽는다.** 그 블로그에 이미 발행된 글에서 실측한 수치가 들어 있다 — 계열 구분, 문단 길이 중앙값, 수평선 사용량, H2 문구 스타일.

레퍼런스 없이 작업하면 섹션 나누는 방식과 문단 길이가 매번 달라진다. 실제로 그래서 이 단계가 생겼다. 이 스킬이 제안하는 모든 것(구간 경계·소제목 문구·리스트/표 전환·수평선)은 **해당 계열의 수치 안에 들어와야 한다.**

레퍼런스를 읽었으면 3단계로 넘어가기 전에 **이 초안이 어느 계열인지 먼저 판정하고 사용자에게 말한다.** 계열을 잘못 잡으면 나머지 제안이 전부 어긋난다 — 서사형 글에 카드형 구조를 씌우면 읽는 맛이 죽고, 회고를 서사형으로 풀면 항목 비교가 안 된다.

레퍼런스 파일이 없으면 이 단계를 건너뛰되, **보고할 때 "구조 레퍼런스가 없어 기존 발행물과의 일관성은 확인하지 못했다"고 명시한다.**

### 1. 초안 읽기 + 현재 구조 파악

`Blog-drafts/[제목].md`를 읽는다. 인자로 경로를 받지 못했으면 어떤 초안인지 사용자에게 묻는다 — 추측해서 아무 파일이나 열지 않는다.

먼저 헤딩이 있는지 기계적으로 확인한다:

```bash
grep -n '^#\{1,6\} ' "Blog-drafts/제목.md"
```

**출력이 비어있으면(평문 초안 — 기본 케이스)**, 2단계를 건너뛰고 대신 **본문 안에 이미 있는 위계 신호를 수집한다.** 사람이 쓴 글은 마크업이 없어도 구조 의도가 문장 안에 남아 있고, 그걸 줍는 게 이 스킬의 핵심 작업이다:

- **번호·순서 표기**: `1.` `2.` `첫째` `두번째` 같은 나열 — 대개 소제목이 되려다 만 것이다
- **버전·단계 표기**: `v1` `v2.2` `1차` `이후` — 글 전체를 관통하는 축일 때가 많다
- **저자가 말로 찍은 경계**: "서론이 길었습니다", "그래서 뭘 만들려고 했느냐", "여기까지가 ~였습니다" — 저자가 이미 구간을 인지하고 있다는 신호
- **반복 구조**: 같은 형태의 사례·질문·인용이 여러 번 나오면 그 자체가 한 구간이다

이 신호들의 줄 번호를 목록으로 만든다. 3단계 구간 나누기의 1차 근거가 된다.

**출력에 헤딩이 있으면**, 구간별 길이도 함께 센다:

```bash
F="Blog-drafts/제목.md"
{ grep -n '^#\{1,6\} ' "$F" | sed 's/:/ /'; echo "$(( $(wc -l < "$F") + 1 )) ."; } | {
  prev=""; prevn=0
  while read -r num text; do
    [ -n "$prev" ] && echo "$prev -> $(sed -n "$((prevn+1)),$((num-1))p" "$F" | grep -c .)줄"
    prev="$text"; prevn="$num"
  done
}
```

> 이 스킬의 bash 스니펫에는 **위치 인자 형태의 토큰(달러 기호 뒤에 숫자)을 쓰지 않는다.** 스킬 인자가 로드 시점에 그 자리를 치환해버려서 명령이 깨진다 — awk에서 레코드 전체를 가리키던 자리가 인자로 받은 파일 경로로 바뀐 사례가 실제로 있었다. 변수는 `${F}` `${prev}`처럼 반드시 이름을 붙여서 쓰고, 레코드 전체가 필요하면 awk 대신 위 셸 루프를 쓴다.

어느 쪽이든, 파악한 현재 구조를 사용자에게 먼저 보여주고 다음 단계로 간다.

### 2. H2/H3 위계가 논리와 안 맞는 지점 찾기 (헤딩이 이미 있을 때만)

아래 유형을 찾아 위치(줄 번호)와 이유를 적는다. **고치지 말고 목록만 만든다.**

- **레벨 점프**: H2 다음에 H4가 오는 식으로 단계를 건너뛴 곳
- **동급이 아닌 것들이 동급**: 같은 H2 아래 놓였지만 하나는 다른 하나의 하위 개념인 경우 (예: "도구 비교"와 "vLLM 설정법"이 나란히 H2)
- **하위 항목이 하나뿐인 H3**: 형제가 없는 H3는 대개 위계가 아니라 강조를 하려던 것이다
- **본문 내용과 헤딩이 어긋난 구간**: 헤딩은 A를 말하는데 아래 문단은 B를 다루는 경우
- **제목(H1) 중복**: 파일명·frontmatter 제목과 본문 H1이 겹치는지

평문 초안이면 이 단계는 건너뛴다. 대신 1단계에서 모은 위계 신호가 3단계의 입력이 된다.

### 3. 구간 나누기 — 소제목이 들어갈 위치 찾기

글을 화제 단위로 끊는다. 판단은 줄 수만이 아니라 **화제 전환이 몇 번 일어났는지**로 한다 — 짧아도 화제가 두 번 바뀌면 경계고, 길어도 한 가지 이야기면 그냥 둔다.

1단계에서 모은 위계 신호를 먼저 경계 후보로 놓고, 그 사이에 신호 없이 화제만 바뀐 지점을 추가한다.

각 경계마다 이렇게 보고한다:
- 위치: 몇 번째 줄, "○○로 시작하는 문단 앞"
- 이유: 여기서 화제가 X에서 Y로 넘어간다
- 제안 레벨: H2인지 H3인지

**주의할 것**:
- **저자가 말로 찍은 경계에 소제목을 넣으면 그 문장과 역할이 겹친다.** ("서론이 길었습니다" 바로 뒤에 소제목을 넣는 경우) 겹친다는 사실을 알리고, 그 문장을 살릴지 사용자에게 묻는다. **문장 삭제는 사용자 몫이므로 임의로 지우지 않는다.**
- **모든 긴 구간에 소제목을 넣지 않는다.** 헤딩이 잘게 쪼개지면 목차만 길어지고 글은 오히려 안 읽힌다. 화제가 실제로 바뀌는 곳만 짚는다.

### 4. 소제목 문구 후보 제시

3단계에서 찾은 각 위치마다 **톤이 다른 후보 3개**를 나란히 준다. 하나만 주지 않는다 — 사용자가 고르는 행위 자체가 자기 목소리를 지키는 장치다.

| 톤 | 성격 | 언제 유리한가 |
|---|---|---|
| 직설형 | 그 구간이 다루는 것을 그대로 명명 | 목차만 훑는 독자에게 내용이 바로 보임 |
| 구어형 | 그 글의 말투를 그대로 이어받음 | 글 전체의 목소리가 뚜렷할 때 |
| 질문형 | 독자의 질문을 그대로 헤딩으로 | 검색·AI 인용 노출에 유리 |

**후보를 만드는 규칙**:
- **그 구간 본문에 이미 있는 어휘로 만든다.** 새 개념어를 끌어오지 않는다 — 저자가 안 쓴 단어가 헤딩에 올라오면 글이 남의 글처럼 읽힌다.
- 글 전체의 어미·말투를 관찰해서 구어형 후보에 반영한다 (반말/존댓말, 밈·감탄사 사용 여부).
- 후보가 마음에 안 들 수 있으므로 **"직접 쓰겠다"는 선택지를 항상 함께 제시**한다.
- 후보 3개가 서로 너무 비슷하면 후보를 준 게 아니다. 세 톤이 실제로 달라야 한다.

### 5. 나열형 → 리스트, 비교형 → 표 후보 찾기

- **리스트 후보**: 한 문단 안에서 항목을 "첫째~, 둘째~", "A도 있고 B도 있고 C도 있다" 식으로 나열한 구간
- **표 후보**: 둘 이상의 대상을 **같은 축**으로 비교하는 구간 (예: 도구 3개를 각각 속도·비용·러닝커브로 서술). 축이 2개 이상이어야 표가 이득이다 — 대상만 여럿이고 축이 하나면 리스트가 낫다.
- **바꾸지 말아야 할 것**: 흐름이 있는 서술(원인→결과, 시행착오 서사, 시간순 에스컬레이션)은 나열처럼 보여도 리스트나 표로 쪼개면 인과와 감정선이 끊긴다. 후보에서 제외하고, **제외했다는 사실과 이유를 보고에 남긴다** — 사용자가 그 판단에 동의하지 않을 수 있다.

각 후보는 **변환 후 모습을 미리 보여주되 파일에는 쓰지 않는다.** 이때도 원문 표현을 그대로 옮겨 담기만 하고 문장을 새로 쓰지 않는다 — 표의 셀에 들어갈 말도 원문에서 잘라온 것이어야 한다. 문장을 줄이거나 다듬어야만 표에 들어가는 항목은, 그 사실을 밝히고 사용자에게 어떻게 줄일지 묻는다.

### 6. 시각 자료 슬롯 제안

글이 텍스트만으로 이어질 때, 그림이 들어가면 이해가 빨라지는 자리를 짚는다. 표기는 `tech-research-card-blog`와 동일한 슬롯 형식을 쓴다 (두 스킬의 산출물이 같은 vault에 섞이므로 형식을 갈라놓지 않는다):

```
{이미지: 유형 | 설명 | 용도}
```

**슬롯이 필요한 자리를 찾는 신호**:
- **단계·버전의 변천**을 문장으로만 설명한 구간 (v1 → v2 → v3, 시도→실패→재설계) → 흐름 다이어그램
- **계층·분류 체계**가 슬래시나 쉼표로 한 줄에 뭉쳐 있는 구간 → 구조도
- **수치·실험 결과**가 문장 안에 흩어져 있는 구간 → 요약 표나 차트
- **화면·결과물**을 말로만 묘사한 구간 → 실측 스크린샷

**유형별 처리**:
- **다이어그램·구조도**: 슬롯만 표시하고, 사용자가 원하면 `design` / `artifact-diagramming` 쪽으로 바로 제작한다.
- **실측 스크린샷**: 사용자만 갖고 있는 자료다. 슬롯을 남기고 "무엇을 찍어야 하는지"만 적어준다. 절대 대신 만들어내지 않는다.
- **일러스트·짤**: 슬롯과 용도만 적는다.

**넣지 말아야 할 것**: 장식용 이미지. 문단마다 그림을 끼우면 글의 리듬이 끊기고 스크롤만 길어진다. 텍스트로 이미 충분히 전달되는 구간에는 슬롯을 만들지 않는다.

### 7. [선택] 사용자가 준 깃헙·문서 링크에서 표 가져오기

**이 단계는 사용자가 URL을 직접 줬을 때만 실행한다.** 스킬이 스스로 검색해서 자료를 찾아오지 않는다 — 그건 구조 정리가 아니라 자료 조사이고, 이 스킬의 범위 밖이다.

링크를 받았으면 README를 받아 표가 있는지 기계적으로 확인한다:

```bash
curl -sS -m 20 -o readme.md "https://raw.githubusercontent.com/OWNER/REPO/HEAD/README.md"
grep -c '^ *|[ :-]*-[ :|-]*|' readme.md   # 마크다운 표 유무
grep -ci '<table' readme.md               # HTML 표 유무
```

`raw.githubusercontent.com`이 안 되면 `WebFetch`로 문서 페이지를 직접 읽는다.

**반드시 지킬 것**:
- **표가 없으면 없다고 보고하고 끝낸다.** README에 표가 있을 거라는 전제는 대체로 안 맞는다 — 주요 리포를 실제로 확인해보면 표 없는 쪽이 다수다. **없는 표를 본문 문장에서 만들어내지 않는다.** 그건 남의 문서를 근거로 내가 새 주장을 짓는 것이다.
- **표가 크면(수십 행·열) 그대로 넣지 않는다.** 어느 행·열만 남길지 사용자에게 묻는다. 추리는 것은 판단이므로 임의로 하지 않는다.
- **출처를 반드시 표 아래 붙인다**: `출처: [저장소명](URL) README (조회: YYYY-MM-DD)`. 남의 표를 출처 없이 옮기지 않는다.
- **가져온 표의 내용은 검증된 사실이 아니다.** README는 오래됐을 수 있고 기능 지원 현황이 바뀌었을 수 있다. 이 단계를 돌았다고 해서 frontmatter의 `status`를 `팩트체크 완료`로 올리지 않는다 — 수치·지원 여부 검증은 `tech-wiki-factcheck`의 일이고, 그쪽을 돌리라고 안내한다.
- **GitHub API(스타 수·라이선스·최종 커밋)에 의존하지 않는다.** 비인증 요청은 rate limit(403)에 걸린다. 필요하면 사용자에게 값을 물어본다.

### 8. 제안 보고

2~7을 하나의 표로 정리해서 보여준다:

| # | 위치(줄) | 유형 | 진단 | 제안 | 승인? |
|---|---|---|---|---|---|
| 1 | 13 | 소제목 | 근황 → 과거 사례로 화제 전환 | H2 삽입 (문구 후보 3개 아래 참고) | |
| 2 | 44 | 위계 | 번호 항목과 설명 문단이 같은 레벨 | 항목을 H3로 올림 | |
| 3 | 66 | 표 후보 | 대상 2개를 2축으로 비교 | 2행 2열 표 | |
| 4 | 84 | 시각 자료 | v1→v3 변천이 문장으로만 설명됨 | 다이어그램 슬롯 삽입 | |

소제목 문구 후보는 이 표 아래에 위치별로 따로 묶어서 보여준다 (표 안에 3개를 다 넣으면 읽히지 않는다).

오탈자는 이 표에 넣지 말고 맨 아래 별도 목록으로 적는다 (구조 제안과 섞이면 승인 단위가 흐려진다).

그리고 사용자에게 **번호로** 승인을 받는다: "몇 번 적용할까?" 전체 일괄 승인도 번호를 다 부르는 것으로 취급한다. 소제목 항목은 **번호 승인 + 문구 선택**이 둘 다 있어야 적용된다.

### 9. 승인된 변경만 적용

- 승인된 항목만 `Blog-drafts/[제목].md`에 적용한다. 승인 안 된 항목은 언급도 남기지 않는다(파일에 TODO 주석을 심지 않는다).
- **적용은 헤딩 줄·리스트 마커·표 마크업·이미지 슬롯의 추가/변경에 한정된다.** 문장 자체는 위치만 옮길 뿐 글자를 바꾸지 않는다.
- 소제목 삽입이 승인됐는데 문구를 아직 못 골랐으면, 문구부터 받고 넣는다. 임시 문구를 대신 넣어두지 않는다.
- 적용 후 헤딩 구조를 다시 뽑아(1단계의 `grep`) 사용자에게 보여준다.

### 10. 기록

`log.md`에 한 줄 추가한다: `| 날짜 | 작업 | 환경 | 근거/결과 | 확인 필요 |`

**환경** 칸에는 이 스킬이 실행된 곳(`Claude Code` / `Cowork` / `claude.ai`)을 반드시 적는다 — 여러 환경에서 같은 vault를 건드릴 수 있어 나중에 추적할 유일한 단서다.

예: `| 2026-08-31 | 블로그 초안 구조 정리 (임베딩 모델 비교) | Claude Code | 평문 초안에 H2 5개·H3 2개 부여, 표 변환 1건, 이미지 슬롯 2건 | 오탈자 2건 미수정 |`

## vault 규칙 (CLAUDE.md를 따른다)

vault의 `CLAUDE.md`가 최종 기준이며, 이 문서와 충돌하면 `CLAUDE.md`를 따른다.

- **경로**: 초안은 `Blog-drafts/[제목].md`에 평평하게(flat). 하위 폴더·번호 코드 파일명을 새로 만들지 않는다.
- **frontmatter에 위키링크 금지.** 구조를 만지다가 `- 원문: [[제목]]` 같은 본문 줄을 frontmatter로 올리지 않는다 — YAML이 리스트로 파싱해 링크가 깨진다. frontmatter에는 `stage`/`created_date`/`status` 같은 순수 메타데이터만.
- **링크에 폴더 경로를 넣지 않는다** (`[[Cards/제목]]` 아니라 `[[제목]]`).
- **새 최상위 문서를 만들지 않는다** (`WORKFLOW.md`, 폴더별 `README.md` 등). 안내는 `index.md`, 이력은 `log.md`뿐이다.
- 파일을 수정했으면 끝내기 전에 링크 검증을 돌린다:

```bash
comm -23 \
  <(grep -rho '\[\[[^]]*\]\]' raw Cards Blog-drafts index.md 2>/dev/null | sed 's/\[\[//; s/\]\]//; s/|.*//' | sort -u) \
  <(find raw Cards Blog-drafts -name "*.md" | sed 's/.*\///; s/\.md$//' | sort -u)
```

출력이 비어있으면 통과. 뭔가 나오면 그게 깨진 링크다.

## 흔한 실수 — 반드시 피할 것

- **"구조를 고치는 김에" 문장을 다듬는 것.** 이 스킬이 실패하는 제일 흔한 방식이다. 사용자가 자기 글을 다시 봤을 때 자기 문장이 아니면 신뢰가 끊긴다.
- **구조 레퍼런스를 안 읽고 시작하는 것.** 0단계를 건너뛰면 이 글만 놓고 보기엔 멀쩡한데 기존 발행물과 따로 노는 결과가 나온다. 섹션 나누는 방식·문단 길이·수평선 사용이 글마다 달라지는 게 그 증상이다.
- **짧은 문단을 "덜 쓴 글"로 보고 합치려는 것.** 서사형에서는 한 문장이 한 문단인 게 정상이고 그게 박자다. 문단을 합치면 문체가 죽는다 — 레퍼런스의 문단 길이 중앙값을 기준으로 판단한다.
- **헤딩이 없다고 "분석할 게 없다"고 판단하는 것.** 평문이 기본 입력이다. 헤딩이 없으면 1단계에서 본문 안의 위계 신호부터 줍는다.
- **소제목 후보를 하나만 주거나, 골라주지 않고 확정해버리는 것.** 후보는 톤이 다른 3개 + "직접 쓰겠다" 선택지가 기본이다.
- **후보 문구에 원문에 없는 개념어를 끌어오는 것.** 헤딩만 남의 글이 되면 글 전체가 어색해진다.
- **모든 긴 구간에 소제목을 넣으려는 것.** 화제가 실제로 바뀌는 곳만 짚는다.
- **서술을 표로 밀어넣는 것.** 표는 같은 축으로 비교될 때만 이득이다. 인과·시간 흐름이 있는 글을 표로 만들면 정보가 아니라 맥락이 사라진다.
- **문단마다 이미지 슬롯을 끼우는 것.** 장식용 이미지는 리듬만 끊는다.
- **사용자가 주지도 않은 링크를 검색해서 자료를 끌어오는 것.** 7단계는 링크를 받았을 때만 돈다.
- **승인 범위를 넘겨 적용하는 것.** "2번 해줘"는 2번만이다. 하는 김에 인접한 3번을 같이 하지 않는다.
